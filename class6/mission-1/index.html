    미션 6-1. 구현과 검토¶

    이번 미션에서 할 것

    • 대표 스토리 [스토리] 새 메뉴 2개를 추가해 선택지 늘리기를 개발자가 분기 story-10에서 구현하고 PR로 검토를 요청합니다.
    • BA가 인수 조건 ①~④를 기준으로 수정 요청과 변경 제안을 하고, 개발자가 반영합니다.
    • BA와 PO가 승인하면 PM이 병합하고, PO가 배포된 웹페이지에서 인수 조건 ①~③을 직접 확인합니다.

    소요 시간 약 15분 실습 장소 팀 리포지토리 lunch-picker-team<번호> 관련 교안 6교시 교안, Actions, 검사 통과와 요구 충족, Pages 배포

    준비¶

    • 5교시에 만든 팀 리포지토리 lunch-picker-team<번호>를 엽니다. 이슈(에픽 3개, 스토리 7개), 마일스톤 MVP, Release v1.0, 팀 Projects 점심 메뉴 추천 팀<번호>의 진행 보드가 있어야 합니다.
    • 대표 스토리 [스토리] 새 메뉴 2개를 추가해 선택지 늘리기의 이슈 번호를 확인합니다. 이 페이지는 #10으로 설명합니다. 번호는 팀마다 다릅니다. 우리 팀 번호가 12번이면 #10은 #12로, story-10은 story-12로 바꿔 읽으세요.
    • 지금 site/menus.json에는 메뉴가 6개 있습니다. 이 미션이 끝나면 8개가 됩니다.
    • PO는 다른 탭에 팀 웹페이지 https://<PO아이디>.github.io/lunch-picker-team<번호>/를 열어 둡니다. 안 열리면 4-3에서 한 Pages 설정(Settings → Pages → Source를 GitHub Actions로)을 다시 확인하세요.
    • 모두 자기 역할 탭을 고르세요. 한 번 고르면 이 가이드의 모든 페이지가 같은 탭으로 바뀝니다.

    3인 팀은

    PO가 PM을 겸합니다. PO 탭과 PM 탭의 할 일을 PO 한 사람이 모두 합니다.

    전체 흐름¶

    순서 누가 무엇을 누구에게 넘김
    ① PM 진행 보드에서 대표 스토리를 개발자에게 배정, Status를 In Progress로 개발자
    ② 개발자 분기 story-10에서 메뉴 2개 추가, 커밋, PR 열기, 리뷰어 지정, 자동 검사 확인 BA, PO
    ③ BA 인수 조건 ①~④ 기준으로 검토, Request changes와 Add a suggestion 개발자
    ④ 개발자 Apply suggestion으로 반영, 답글, 다시 리뷰 요청 BA
    ⑤ BA Approve PO
    ⑥ PO 최종 Approve PM
    ⑦ PM Squash and merge, 분기 삭제, 이슈와 진행 보드 확인 PO
    ⑧ PO Actions 배포 확인, 배포된 웹페이지에서 인수 조건 ①~③ 확인, 결과 댓글 팀 전체

    역할별 할 일¶

    아래에서 내 역할 탭을 누릅니다. 단계마다 맨 위 언제 시작하나요? 상자를 먼저 봅니다.

    • 바로 시작합니다라고 되어 있으면 지금 시작합니다.
    • 누군가를 기다리는 단계라면 상자에 적힌 화면을 확인합니다. 아직이면 앞 사람이 하는 중이니, 탭 맨 아래 기다리는 동안 할 일을 하며 기다립니다.
    • 내 단계가 끝나면 적힌 대로 다음 사람을 @아이디로 멘션하거나 말로 알립니다. 다음 사람은 그 알림이 시작 신호입니다.

    입력 예시는 그대로 써도 되고, 팀 상황에 맞게 고쳐도 됩니다. #10, story-10 같은 번호는 여러분 팀 대표 스토리의 실제 이슈 번호로 바꾸세요.

    ① 대표 스토리 확인

    언제 시작하나요?

    • 미션 시작과 동시에 합니다. PM이 보드를 옮기는 동안 함께 봅니다.
    1. PM이 진행 보드에서 대표 스토리를 In Progress로 옮길 때 함께 봅니다. 5교시에 내가 Must로 정한 이유 댓글이 스토리에 있는지 확인합니다.

    ⑥ 최종 승인 (BA가 Approve한 뒤)

    언제 시작하나요?

    • BA가 Approve하고 나를 멘션하면 시작합니다.
    • 아직이면: PR 병합 상자에 BA의 승인(초록 체크와 approved)이 없으면 BA가 아직 검토 중입니다.
    1. 리포지토리 위쪽 Pull requests 탭 → 개발자가 연 PR 클릭
    2. Conversation(대화) 탭에서 BA의 리뷰와 개발자의 답글을 읽고, 변경 내용이 스토리의 의도("늘 가던 곳 말고 새 메뉴도 후보로")와 맞는지 봅니다.
    3. Files changed 탭 → 오른쪽 위 초록 Submit review(리뷰 제출, 화면에 따라 Review changes) 클릭 → Finish your review 창이 열립니다

    4. 창 위쪽 Leave a comment 칸에 아래 예시를 입력합니다.

      BA가 인수 조건 ①~④로 검토하고 수정 요청이 반영된 것을 확인했습니다. 스토리 의도와 맞습니다.
병합 후 배포된 웹페이지에서 ①~③을 직접 확인하겠습니다. 최종 승인합니다.

    5. 같은 창에서 세 가지 중 Approve(승인)를 고르고(기본값은 Comment), 창 아래 초록 Submit review(리뷰 제출)를 클릭합니다. 창 모양은 실습 3-3 STEP 3 그림과 같습니다.

    6. PM에게 알립니다. PR 화면(Conversation 탭) 맨 아래 댓글 칸에 @PM아이디 최종 승인했습니다. 병합 부탁드립니다.라고 남겨도 됩니다.

    확인: PR의 Conversation 탭에 <PO아이디> approved these changes가 보입니다.

    ⑧ 배포된 웹페이지에서 인수 조건 확인 (PM이 병합한 뒤)

    언제 시작하나요?

    • PM이 병합하고, Actions 탭의 웹페이지 배포가 초록 체크가 되면 시작합니다.
    • 아직이면: PR 제목 아래 표시가 보라색 Merged가 아니거나, 배포가 노란 점이면 기다립니다.

    자동 검사와 BA 리뷰는 PR 안에서 본 것입니다. 사용자가 실제로 보는 화면에서 정말 되는지는 PO가 배포된 웹페이지에서 확인합니다.

    1. 리포지토리 위쪽 Actions 탭 클릭
    2. 왼쪽 목록에서 웹페이지 배포 클릭. 맨 위 실행 기록의 제목이 방금 병합한 PR 제목인지 봅니다.
    3. 노란 원(실행 중)이 초록 체크(완료)로 바뀔 때까지 1~2분 기다립니다.
    4. 미리 열어 둔 웹페이지 탭으로 가서 강력 새로 고침합니다. Windows는 Ctrl+Shift+R, Mac은 Cmd+Shift+R

    5. 인수 조건 ①~③을 하나씩 직접 확인합니다.

      인수 조건 웹페이지에서 할 일 이렇게 보이면 통과
      ① 예산, 거리 칸을 비운 채로 카드를 셉니다 메뉴 카드가 8개
      ② 비빔밥, 마라탕 카드를 읽습니다 종류, 가격, 거리가 보이고 비빔밥에 "혼밥 가능"
      ③ 예산 칸에 10000을 입력합니다 마라탕(10,000원)이 보임

    6. 대표 스토리 이슈(이미 Closed)에 결과 댓글을 남깁니다. 모두 통과했다면:

      [PO 확인] 배포된 웹페이지에서 인수 조건을 확인했습니다. https://<PO아이디>.github.io/lunch-picker-team<번호>/
- ① 메뉴 카드 8개: 통과
- ② 비빔밥, 마라탕 카드에 종류, 가격, 거리 표시, 비빔밥 "혼밥 가능": 통과
- ③ 예산 10000 입력 시 마라탕 보임: 통과

      통과하지 못한 것이 있으면 무엇이 어떻게 보였는지 적고 개발자를 멘션합니다. 이슈를 다시 열려면 Reopen issue를 누릅니다.

      [PO 확인] ③ 미통과: 예산 10000을 넣으면 마라탕이 보이지 않습니다. 화면에는 가격이 1,000원으로 나옵니다.
@개발자아이디 확인 부탁드립니다.

    확인: 대표 스토리 이슈에 [PO 확인] 댓글이 있고, ①~③이 모두 통과입니다.

    기다리는 동안 할 일

    • 대표 스토리의 인수 조건 ①~③을 다시 읽고, 웹페이지에서 무엇을 보면 "다 됐다"고 할지 정해 둡니다. 지금 웹페이지의 카드가 6개인 것도 미리 봐 둡니다.
    • 다음 미션 6-2의 변경 요청이 들어오면 PO가 가장 먼저 움직입니다. 미션 6-2의 PO 탭을 미리 읽어 두세요.

    ① 대표 스토리 배정하기

    언제 시작하나요?

    • 바로 시작합니다. 6-1에서 가장 먼저 움직이는 사람입니다.

    이번 미션에서 구현할 스토리는 5교시에 정한 대표 스토리 [스토리] 새 메뉴 2개를 추가해 선택지 늘리기입니다. 다른 Must 두 개는 Starter에 이미 있으므로 구현하지 않습니다.

    1. 리포지토리 위쪽 Projects 탭 → 점심 메뉴 추천 팀<번호> 클릭 → 뷰 탭에서 진행 보드 클릭
    2. Todo 열에서 대표 스토리 카드를 찾습니다. (Status가 비어 있으면 No Status 열에 있습니다.)
    3. 카드를 클릭해 오른쪽에 열리는 이슈 창에서 Assignees(담당자) → 개발자 아이디 선택
    4. 같은 창의 Status(상태)를 In Progress로 바꿉니다. 카드를 In Progress 열로 끌어다 놓아도 됩니다.

    5. 대표 스토리 이슈(#10)에 댓글로 개발자에게 넘깁니다. 카드를 눌러 열린 오른쪽 이슈 창 맨 아래 댓글 칸에 써도 되고, 이슈 제목을 눌러 이슈 화면에서 써도 됩니다.

      @개발자아이디 이번 스프린트 첫 구현으로 대표 스토리(#10)를 배정합니다.
분기 이름은 story-10으로 만들어 주세요. 완료 기준은 본문의 인수 조건 ①~④입니다.

    확인: 진행 보드에서 대표 스토리 카드가 In Progress 열에 있고 개발자 프로필 사진이 붙어 있습니다.

    ⑦ 병합하기 (PO가 최종 승인한 뒤)

    언제 시작하나요?

    • PO가 최종 승인하고 나를 멘션하면 시작합니다.
    • 아직이면: PR 병합 상자에 승인이 BA와 PO 두 개가 보이지 않으면 기다립니다.
    1. Pull requests 탭 → 해당 PR 클릭
    2. 아래쪽에 BA와 PO의 승인, 자동 검사 check 통과(초록 체크)가 모두 보이는지 확인합니다.
    3. Merge pull request 버튼 오른쪽 화살표(▼) 클릭 → Squash and merge(커밋을 하나로 합쳐 병합) 선택
    4. Squash and merge 클릭 → 커밋 메시지는 그대로 두고 Confirm squash and merge(병합 확인) 클릭
    5. 보라색 Merged 표시가 뜨면 바로 옆 Delete branch(분기 삭제) 클릭
    6. Issues 탭으로 가서 해당 스토리 이슈가 Closed(닫힘)인지 확인합니다.
    7. Projects → 진행 보드에서 대표 스토리 카드가 Done 열로 자동으로 옮겨졌는지 확인합니다.
    8. 병합한 PR 화면(Conversation 탭) 맨 아래 댓글 칸에 PO에게 알립니다. @PO아이디 병합했습니다. 배포 확인 부탁드립니다.

    확인: PR이 보라색 Merged, 대표 스토리 이슈가 Closed, 진행 보드의 카드가 Done입니다.

    왜 Squash and merge인가요?

    개발자의 커밋과 제안 반영 커밋이 여러 개여도, main에는 "스토리 하나 = 커밋 하나"로 깔끔하게 남습니다. 3교시에 본 병합 방식 중 하나입니다. 나중에 이력 감사에서 이 커밋 하나만 찾으면 됩니다.

    기다리는 동안 할 일

    • 대표 스토리 이슈가 개발자에게 배정되고 진행 보드에서 In Progress를 거쳐 Done이 되었다
    • 분기 story-10(우리 팀 번호)에서 PR이 열렸고, 본문에 Closes #10과 인수 조건 ①~④ 체크리스트가 있다
    • PR에 자동 검사 check 초록 체크가 있다
    • PR에 인수 조건과 연결된 BA의 Request changes 1회 이상, Add a suggestion 1개 이상이 있다
    • 개발자가 Apply suggestion으로 반영하고 다시 리뷰를 요청했다
    • BA와 PO가 Approve했다
    • PM이 Squash and merge로 병합하고 분기를 삭제했다
    • 이슈가 자동으로 Closed 되었다
    • 팀 웹페이지에 메뉴 카드가 8개 보이고, PO가 인수 조건 ①~③ 확인 결과를 대표 스토리 이슈에 댓글로 남겼다

    막히면¶

    병합 뒤 Code 탭에 Your main branch isn't protected 안내가 떠요

    GitHub가 리포지토리 주인(PO)에게 보여 주는 추천 안내입니다. 협업자가 생기고 PR이 병합되기 시작하면 "main을 보호하는 규칙을 만들어 보세요"라고 권합니다. 오류가 아닙니다. 지금은 Dismiss(닫기)를 누르거나 그대로 둡니다. Protect this branch는 누르지 않습니다. main 보호 규칙은 7교시 실습 7-2에서 팀이 함께 만듭니다.

    Reviewers 목록에 팀원 이름이 안 나와요

    팀원이 협력자 초대를 아직 수락하지 않은 경우입니다. PO가 Settings → Collaborators에서 상태를 확인하고, 팀원은 메일이나 https://github.com/notifications에서 초대를 수락합니다.

    BA나 PO 화면에 Approve 선택지가 없어요

    자기가 연 PR에는 승인할 수 없습니다. PR을 연 사람이 개발자인지 확인하세요. 또는 Files changed 탭에 들어가야 Submit review(화면에 따라 Review changes) 버튼이 보입니다.

    Add a suggestion 아이콘이 안 보여요

    줄 옆 +로 연 댓글 창에서만 보입니다. PR 맨 아래 일반 댓글 칸에는 없습니다. 아이콘을 못 찾으면 댓글에 직접 ```suggestion으로 시작하는 블록을 써도 됩니다.

    자동 검사가 '[실패] site/menus.json이 올바른 JSON 형식이 아닙니다.'로 실패해요

    쉼표 문제가 가장 흔합니다. 메뉴 줄 끝마다 쉼표가 있고, 마지막 메뉴 뒤에만 쉼표가 없어야 합니다. 큰따옴표(")가 짝이 맞는지, true, false에 따옴표를 붙이지 않았는지도 보세요.

    병합했는데 이슈가 안 닫혀요

    Closes #10을 PR 제목에만 쓰고 본문에 안 썼거나, 번호가 틀린 경우입니다. 이슈를 직접 열어 Close issue로 닫고, 진행 보드의 카드도 Done으로 옮기세요. 다음 PR부터는 본문에 씁니다.

    진행 보드의 카드가 Done으로 안 옮겨져요

    4-2에서 설정한 자동화(Item closed → Done, Pull request merged → Done)가 팀 Projects에는 꺼져 있을 수 있습니다. Projects 오른쪽 위 Workflows → Item closed를 켜거나, 이번에는 진행 보드에서 카드를 직접 Done으로 옮기세요.

    웹페이지에 변경이 안 보여요

    Actions 탭에서 웹페이지 배포가 아직 노란 원이면 기다립니다. 초록 체크인데도 그대로면 브라우저 캐시 때문이니 강력 새로 고침(Ctrl+Shift+R 또는 Cmd+Shift+R)을 합니다. 빨간 X면 Settings → Pages에서 Source가 GitHub Actions인지 확인하고, Actions 탭에서 웹페이지 배포 → Run workflow로 다시 실행합니다.

    다음 미션으로 넘어가기 전에¶

    • 병합된 PR과 닫힌 이슈는 지우지 마세요. 미션 6-3 이력 감사에서 링크로 씁니다.
    • 이제 site/menus.json에는 메뉴가 8개(기존 6개와 비빔밥, 마라탕) 있습니다. 미션 6-2는 이 8개를 기준으로 합니다.
    • 시간이 남으면 개발자 탭의 선택 과제(예시 2, 3)를 같은 흐름으로 진행해도 됩니다. 강사가 변경 요청을 발표하면 바로 미션 6-2로 넘어갑니다.
