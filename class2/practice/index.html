    혼자 해보기¶

    목표

    킥오프 회의록을 읽고, 아직 이슈가 되지 않은 내용을 스스로 이슈로 등록합니다.

    • 회의록의 "결정하지 못한 것" 2개를 질문 라벨 이슈로 등록합니다.
    • 회의록이나 현업 요청의 요구 1개를 사용자 스토리 템플릿으로 등록합니다.
    • 세 이슈 모두 마일스톤 MVP에 묶습니다.

    docs/01_킥오프_회의록.md를 열어 맨 아래 결정 사항과 결정하지 못한 것을 먼저 읽어 보세요.

    # 킥오프 회의록: 점심 메뉴 추천 서비스

- 일시: 월요일 오후 2시, 3층 소회의실
- 참석: 박지은(경영지원팀, 요청자), 이민호(영업1팀), 최수진(개발팀), 정다은(기획팀)
- 작성: 정다은

---

## 1. 서비스 목적

- 박지은: 점심 메뉴 정하는 데 15~20분씩 쓰는 걸 줄이고 싶다. 5분 안에 정하는 게 목표.
- 정다은: 그럼 성공 기준은 "메뉴 결정 시간 5분 이내"로 잡으면 되겠다.

## 2. 메뉴 정보

- 박지은: 메뉴 이름, 종류, 가격, 거리만 있으면 된다.
- 이민호: 사진도 있으면 좋겠는데, 없어도 괜찮다.
- 최수진: 메뉴 데이터는 처음엔 우리가 직접 정리해서 넣는 걸로 하자. 식당 사이트에서 자동으로 가져오는 건 어렵다.
- 정다은: 식당 정보 자동 수집은 이번에는 안 해도 되는 걸로 정리.

## 3. 가격

- 박지은: 점심값은 만 원 이하만 보여 주면 된다. 그 이상은 아무도 안 먹는다.
- 이민호: 그런데 우리 팀은 금요일에 회식 겸 점심을 자주 해서, 만 원 넘는 메뉴도 추천해 줬으면 한다.
- (결론 못 냄. 다음에 다시 이야기하기로 함)

## 4. 추천 방식

- 박지은: 못 고를 때는 그냥 하나만 딱 골라 주면 좋겠다.
- 이민호: 하나만 골라 주면 다들 마음에 안 든다고 할 거다. 후보를 서너 개 보여 주고 팀원들이 투표하는 게 낫다.
- 최수진: 투표는 사람마다 로그인을 해야 해서 일이 커진다.
- 정다은: 로그인 기능은 이번에는 안 해도 되는 걸로 하자.
- (추천을 하나로 할지 여러 개로 할지는 결론 못 냄)

## 5. 거리

- 박지은: 걸어서 10분 안쪽이면 된다.
- 최수진: 거리는 미터로 넣을지 분으로 넣을지 정해야 한다. 일단 미터로 넣자.
- 이민호: 비 오는 날에는 가까운 데가 더 중요하다.

## 6. 기타

- 이민호: 혼밥 가능한지 표시는 꼭 있었으면 좋겠다.
- 박지은: 웹페이지 하나로 열리면 충분하다. 앱은 필요 없다.
- 정다은: 첫 출시는 최대한 작게 하고, 써 보고 나서 늘리자.

## 결정 사항

1. 메뉴 데이터는 직접 정리해서 넣는다.
2. 웹페이지 하나로 만든다.
3. 식당 정보 자동 수집과 로그인 기능은 이번에는 하지 않는다.
4. 첫 출시는 최대한 작게 한다.

## 결정하지 못한 것

1. 만 원이 넘는 메뉴도 보여 줄지
2. 추천을 하나만 할지, 여러 개 후보를 보여 줄지

    완료 조건¶

    • 질문 라벨이 붙은 열린 이슈가 2개 있습니다. (만 원 넘는 메뉴, 추천 개수)
    • 각 질문 이슈 본문에 누가 어떤 의견이었는지가 들어 있습니다.
    • 사용자 스토리 템플릿으로 만든 이슈가 1개 더 있습니다. 제목이 [스토리]로 시작하고 기능 라벨이 붙어 있습니다.
    • 세 이슈 모두 마일스톤이 MVP입니다.
    • 이슈 목록 검색창에 is:issue label:질문 milestone:MVP를 넣으면 질문 이슈 2개가 나옵니다.
    힌트 1

    "결정하지 못한 것"은 회의록 맨 아래에 두 줄로 있습니다. 하나는 3. 가격, 다른 하나는 4. 추천 방식 절에서 나온 이야기입니다. 질문 이슈는 템플릿 고르는 화면에서 Blank issue로 만들고, 사용자 스토리는 사용자 스토리를 고릅니다.

    힌트 2

    질문 이슈는 결정해야 할 것을 제목에 질문 형태로 쓰면 좋습니다. 본문에는 의견을 사람별로 정리하고, 결정해야 할 사람을 적습니다. 사용자 스토리로 쓸 만한 요구는 아직 이슈가 없는 것을 고릅니다. 예: 현업 요청 1번 "회사 근처 식당 메뉴를 한눈에", 6번 "팀원 투표".

    힌트 3

    사이드바 설정은 이렇게 합니다.

    이슈 Labels Milestone
    질문 이슈 2개 질문, 우선순위-상 MVP
    사용자 스토리 1개 기능(자동), 우선순위-중 MVP

    담당자는 모두 내 아이디로 둡니다. 확인은 Issues 탭 검색창에 is:issue label:질문 milestone:MVP를 넣어 합니다.

    확인 퀴즈¶

    Q1. README.md를 리포지토리 첫 화면에 자동으로 보이게 하려면 어디에 두어야 하나요?
    1. docs 폴더 안
    2. 리포지토리 맨 위(최상위) 폴더
    3. .github/ISSUE_TEMPLATE 폴더 안
    4. 어디에 두든 자동으로 보인다

    정답: 2

    GitHub는 리포지토리 맨 위 폴더의 README.md를 파일 목록 아래에 자동으로 펼쳐 보여 줍니다. 하위 폴더에 있는 README는 그 폴더를 열었을 때 보입니다. 그래서 README는 프로젝트의 첫 화면, 표지 역할을 합니다.

    Q2. 다음 중 이슈보다 파일(문서)로 커밋해 두는 것이 더 어울리는 것은?
    1. "만 원 넘는 메뉴도 보여 줄까요?"라는 질문
    2. 개발자가 BA에게 묻는 인수 조건 확인 요청
    3. 확정된 킥오프 회의록
    4. 이번 주에 처리할 버그

    정답: 3

    오래 남겨야 하는 확정 문서는 파일로 커밋해 Git의 이력으로 관리합니다. 질문, 요청, 할 일처럼 대화하며 진행하고 끝나면 닫는 것은 이슈로 관리합니다. "문서는 기록으로 남기는 것, 이슈는 대화하며 진행하는 것"입니다.

    Q3. lunch-practice 리포지토리를 다른 컴퓨터로 복제(clone)하면 이슈 #1~#5도 함께 따라가나요?
    1. 네, 리포지토리에 있는 것은 모두 따라간다.
    2. 아니요, 이슈는 GitHub 서비스가 관리하는 데이터라 따라가지 않는다.
    3. 열린 이슈만 따라간다.
    4. 라벨은 따라가고 이슈는 따라가지 않는다.

    정답: 2

    복제하면 Git이 관리하는 파일, 커밋, 분기, 태그만 따라갑니다. 이슈, 라벨, 마일스톤, PR 대화, Projects는 GitHub 서비스 안에 있어서 따라가지 않습니다. 단, 이슈 템플릿 파일 .github/ISSUE_TEMPLATE/user-story.md는 파일이라서 따라갑니다.

    Q4. 마일스톤(Milestone)의 용도로 가장 알맞은 것은?
    1. 이슈의 종류(기능, 질문)를 표시한다.
    2. 이슈를 맡은 사람을 지정한다.
    3. 함께 출시할 이슈를 묶고, 그중 몇 퍼센트가 끝났는지 본다.
    4. 큰 이슈를 작은 이슈로 쪼갠다.

    정답: 3

    마일스톤은 MVP처럼 함께 내보낼 이슈 묶음이고, 묶인 이슈 중 닫힌 비율로 진행률을 자동 계산합니다. 1번은 라벨(Labels), 2번은 담당자(Assignees), 4번은 하위 이슈(Sub-issues)의 용도입니다.
